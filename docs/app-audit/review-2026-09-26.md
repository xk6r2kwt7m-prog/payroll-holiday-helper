# App-wide review and staged improvement draft — 26 September 2026

Base reviewed: `2407c3a3f925d65adc42eceb290706beca2d4191`. This is a source-level review and prioritised implementation plan, not a certification of the live app. No production database, real staff record, email or published app was changed. Grand-total policy remains HELD. PR #14's release-review corrections are separate from this branch.

## Decision

Stabilise the existing workflows before another broad redesign. The highest-value improvements are predictable permissions, honest loading/error states, one atomic result for important saves, and one clear next action per screen. Smaller modules help constrain changes, but do not replace server checks, transactions or realistic tests.

This draft implements only the development guardrails described in `architecture.md`: an import/size check, CI step and change-scope PR template. The application defects below are queued corrections, not silently bundled runtime changes. Lovable can take them one at a time with the acceptance tests specified here.

## Coverage and evidence limits

The inventory covers all 58 page files and 34 server function entry points; see `inventory.md`. Routing and shared hooks were mapped. Targeted source reviews covered access, time entries, scheduling/marketplace, financial reporting, people/onboarding, contracts, documents/compliance, learning, announcements, transfers and recruitment. Existing release preparation and PR #14 findings inform payroll/holiday risk, but their live installation has not been independently established.

Inventory coverage does not mean every line, SQL migration, dependency or page was exhaustively tested. No authenticated live browser journey, mobile screenshot review, production policy inspection, load test, backup verification or external provider test was performed in this pass. Assertions about vulnerabilities below are limited to the code paths observed; live exploitability depends on deployed RLS, triggers, grants and feature availability. User experience proposals need signed-in previews with fictional data before implementation approval.

## Experience acceptance standard

Use synthetic staff on 360–390px phones and desktop, keyboard-only and 200% zoom. A manager should identify the blocked action and next step without opening several tabs. A staff member should see only tasks relevant to them, accepted data should stay accepted, and deadlines should say why they matter. Preserve entered values after validation errors. Provide accessible labels, visible focus and non-colour status cues; announce save/error states. Test loading, empty, failed, stale and partial states separately. Destructive actions need an explicit scope and retained audit, not a vague confirmation.

Define measurable baselines before targets: time to complete joining, repeated information requests, manager review time, duplicate submissions, failed commands, outstanding delivery failures and route loading. Measure with minimal personal data; do not add intrusive staff tracking to this draft.

## Verification and limitations

The architecture checker has eight passing behavioural tests and passes against the unchanged application source. Validation on this branch: 1,876 app tests across 138 files passed; TypeScript, financial-boundary checks and production build passed. Eight additional architecture tests passed. The production build still reports large chunks and dependency annotation warnings; route splitting remains a separate proposal. New tests check the new guardrail; they do not validate every finding in this report. The code defects require their own regression reproductions when implemented.

A perfectly error-free promise would be misleading. Release confidence comes from scoped changes, durable server rules, synthetic failure/concurrency tests, clear recovery paths and observation after an authorised release.
